# 01. Agent Evaluation

> 서로 다른 Agent 구현을 같은 입력과 기준으로 재현 가능하게 비교할 수 있는가?

## 프로젝트 정의

- **상태:** `planned`
- **참여자:** `@ukkhnn`, `@us788`
- **역할:** 모든 핸즈온의 공통 계약·평가·관측 기반
- **선행 프로젝트:** 없음
- **후행 프로젝트:** 나머지 모든 프로젝트

## 배경과 목적

각 Agent가 “작동했다”는 주관적 판단을 넘어서 성공률, 도구 선택, 비용, 지연시간과 안전성을 같은 형식으로 측정합니다. 이후 프로젝트가 이 결과 형식을 사용해야 Router와 통합 시스템에서 직접 비교할 수 있습니다.

## 과제 명세

### 입력

- `TaskRequest` 형식의 평가 태스크
- 구현이 생성한 `AgentResult`와 `ToolTrace`
- 기대 결과, 허용 도구, 금지 행동과 판정 규칙

### 필수 구현

- JSON Schema 또는 모델 기반 공통 계약 검증
- 구현을 반복 호출하는 평가 runner
- 정확 일치·테스트 통과·필수 근거 확인 등 결정적 grader
- 선택적인 LLM grader와 결정적 평가의 결과 분리
- 성공·실패·예외를 포함한 결과 집계

### 산출물

- 공통 평가 데이터 예제 20개 이상
- 구현별 `EvaluationRecord`
- 성공률·p50/p95 latency·비용·도구 정확도 비교표
- 실패 유형과 회귀 결과

### 포함 범위

- 공통 schema와 validation
- 로컬에서 반복 가능한 평가 실행
- JSONL·CSV·Markdown 형태의 작은 결과 리포트

### 제외 범위

- 평가 대상 Agent의 핵심 기능 구현
- LLM grader만으로 성공 여부 결정
- 실패 결과 삭제 또는 정답의 사후 변경

## 공통 계약

- 입력: `TaskRequest`
- 결과: `AgentResult`
- 도구 실행: `ToolTrace`
- 평가: `EvaluationRecord`

계약 원본은 `../../common/contracts/`에서 관리합니다.

## 권장 기술

- Python 3.11 이상
- Pydantic 또는 `jsonschema`
- pytest
- Pandas 또는 DuckDB
- 선택적으로 OpenAI Evals나 별도 LLM grader

## 디렉터리 사용

- `shared/`: 평가 태스크 schema와 프로젝트 고유 fixture
- `implementations/ukkhnn/`: `ukkhnn`의 평가 구현
- `implementations/us788/`: `us788`의 평가 구현
- 여러 프로젝트가 공유하는 runner는 검증 후 `../../common/evaluation/`로 이동

## 평가 기준

| 지표 | 측정 방법 | 목표 |
| --- | --- | --- |
| schema 검증 | 정상·비정상 fixture | 판정 100% 일치 |
| 관측성 | 필수 telemetry 누락률 | 0% |
| 결정성 | 같은 결정적 입력 반복 | 결과 일치 |
| 실패 보존 | 예외·실패 레코드 확인 | 누락 0건 |
| 리포트 | 두 구현 비교표 생성 | 자동 생성 |
