# Hands-on에서 Personal AI로

전문 Agent가 한 번의 요청을 잘 처리하는 것과, 사용자가 며칠 동안 여러 기기에서 계속 쓰는 작업공간을 만드는 것은 다른 검증 문제다. 01~09는 전자를 다루고, 10~17은 실행 상태·권한·설정·파일·접속을 잃지 않는 기반을 다룬다. 이 두 흐름을 연결한 제품 적용 대상이 [Personal AI](https://github.com/ukkhnn/personal-ai)의 `agent-workspace`다.

## 학습 경로를 정리한 방식

이 문서와 신규 실험은 기존 결과 및 현재 제품을 함께 살펴 재구성한 학습 경로다. 아래 날짜는 요청된 학습·커밋 배치 슬롯이며 실제 측정 시각의 증거가 아니다. 실행 결과 JSON의 `evaluated_at` 또는 해당 실험의 실제 실행 시간 필드를 기준으로 재현 여부를 판단한다. 01~09의 기존 이력은 수정하지 않았다.

Personal AI의 최초 기획·구현 커밋은 2026-10-28에 있다. 따라서 10-16은 제품에 필요한 기반 개념을 설명하는 선행 학습 흐름으로, 17의 10월 30일 슬롯은 이미 시작된 제품으로의 인계·차이 검증으로 배치했다. 새 실험이 당시 제품을 실제로 탄생시켰다는 역사적 주장이나 당시의 실험 로그는 만들지 않는다.

## 1. 전문 Agent의 가능성과 한계 — 01~09

- 01은 평가·관측과 비교 기준을 만들었다.
- 02~05는 로컬 모델, 검색, 화면 이해, 연구의 개별 품질을 확인했다.
- 06은 작업을 맡길 경로를 선택했다.
- 07~09는 브라우저·코딩·보안 검사 경계를 다뤘다.
- Integration v1은 라우팅과 공통 계약, 오류 시 차단을 연결했다. 저장된 결과 재현과 일부 실제 실행을 구분했다.

이 단계에서 남은 질문은 모델 성능만이 아니었다. 창을 닫으면 작업은 어떻게 되는가? 실행 중 새 지시를 보내면 어떻게 되는가? 지난번 승인을 다른 작업에 재사용할 수 있는가? 같은 저장소의 두 작업은 파일을 덮어쓰지 않는가?

## 2. 일회성 실행에서 지속하는 작업공간으로 — 10~16

| 슬롯 | 실험 | 검증 질문 | 제품에 가져갈 판단 |
|---|---|---|---|
| 10/05 | [10 Runtime Adapter](../experiments/10-runtime-adapter/) | 엔진을 교체해도 작업·세션 의미를 유지할 수 있는가? | 자체 ID와 엔진 ID, 지원 기능을 분리 |
| 10/06 | [11 Session Persistence](../experiments/11-session-persistence/) | 재시작 후 작업과 진행 기록을 복원할 수 있는가? | 상태 저장과 프로세스 실행 수명을 분리 |
| 10/07 | [12 Durable Instructions](../experiments/12-durable-instructions/) | 새 지시를 잃거나 중복 실행하지 않을 수 있는가? | 대기·전달·완료·불확실 상태와 중단 제어를 구분 |
| 10/20 | [13 Approval Boundary](../experiments/13-approval-boundary/) | 승인이 정확한 작업과 행동에만 적용되는가? | 소유자·내용·버전·기한·1회 사용을 결부 |
| 10/21 | [14 Harness & Memory](../experiments/14-harness-memory/) | 재사용 설정과 기억이 다른 작업에 섞이지 않는가? | 버전별 snapshot, 지원 차이, 기억의 범위·출처 |
| 10/25 | [15 Worktree Isolation](../experiments/15-worktree-isolation/) | 병행 개발의 파일 변경을 분리하고 보존할 수 있는가? | 작업별 worktree, 미커밋 변경 보호, OS 격리와 구별 |
| 10/27 | [16 Central Session Client](../experiments/16-central-session-client/) | 다른 클라이언트가 같은 작업을 안전하게 이어 보는가? | 중앙 상태, 소유권, 커서 재접속, 중단 확인 분리 |
| 10/30 | [17 Personal AI Handoff](../experiments/17-personal-ai-handoff/) | 검증 결과를 제품 요구사항에 연결해 인계할 수 있는가? | 소스 전달과 실행 상태 이전을 구별하고 차이를 기록 |

## 3. 제품으로의 연결

```text
01~09: 전문 Agent의 품질과 실행 경계
            ↓
Integration v1: 요청별 라우팅·계약·보안 게이트
            ↓
10~12: 교체 가능한 엔진 + 영속 상태 + 지시 전달
            ↓
13~15: 행동별 승인 + 설정·기억 + 작업 파일 분리
            ↓
16: 중앙 실행 상태를 여러 클라이언트에서 조회·제어
            ↓
17: 재현 결과와 미검증 항목을 Personal AI에 인계
            ↓
personal-ai/agent-workspace: 지속해서 사용하는 개발 작업공간
```

제품은 이 실험 코드의 복제본이 아니다. 실험은 설계 선택의 근거와 실패 조건을 제공하며, 제품은 UI·실행 엔진·운영·데이터 보존을 함께 책임진다. 실제 제품 구현과 향후 후보의 구분은 17의 고정된 소스 기준표로 확인한다.

## 적용과 미검증 항목

새 실험의 HTTP 통신, 저장·재시작, 파일 변경과 Git worktree는 로컬 임시 환경에서 실제 실행한다. LLM 판단 품질이나 운영 배포를 fixture 성공으로 대체하지 않는다.

- Mac mini 배포, Tailscale/HTTPS, 실제 모바일·다른 기기 접속은 별도 운영 검증이다.
- 실행 중 프로세스와 외부 엔진 세션은 Git push로 이전되지 않는다.
- worktree는 파일 분리이며 프로세스·권한·포트·DB 격리를 보장하지 않는다.
- 승인 기록 저장과 실제 외부 부작용 사이의 exactly-once는 가정하지 않는다.
- 제품의 자동 커밋·push·병합, 전체 하네스 편집, 백업·자동 시작은 제품 쪽에서 따로 완성해야 한다.

## 재현

Node.js 22.19 이상과 Git으로 새 실험을 실행한다. 외부 npm 패키지나 유료 모델 키가 필요하지 않다.

```sh
node integration/run-workspace-bridge.mjs
```

각 실험 폴더에서도 독립적으로 `npm test`, `npm run evaluate`를 실행할 수 있다. 통합 실행은 전용 결과 디렉터리와 임시 파일을 사용하며 Personal AI 소스나 사용자 작업 저장소를 변경하지 않는다.
